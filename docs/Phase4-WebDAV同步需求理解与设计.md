# 时物 App · 同步功能需求理解与设计文档（WebDAV / 局域网 NAS）

> 状态：待评审 · 2026-08-01
>
> 关联：Phase3 多清单已上线；本文档在 Room v2（items / wishes / lists / categories）的现状上演进。

## 一、需求理解

### 1.1 使用场景

- NAS 开启 WebDAV，家里局域网内两台设备（手机 + 平板）都装有「时物」；
- 在家时通过 NAS 同步，让两台设备数据一致；
- 外出时设备离线各自使用：修改已有物品、新增物品 / 心愿 / 清单；
- 回家后触发同步 / 拉取，要求不出现「版本问题」——数据不丢、不乱、结果确定。

### 1.2 目标（准确表述）

| 目标 | 说明 |
| --- | --- |
| 双向同步 | 一次同步 = 下载远端 + 本地合并 + 上传合并结果，同时完成拉取与推送 |
| 离线优先 | 任一设备离线期间可正常增删改，不受同步影响 |
| 最终一致 | 同步完成后各设备收敛到同一份数据 |
| 不丢数据 | 离线期间的任何修改都不会被静默覆盖或丢失 |
| 确定性 | 相同数据 + 相同操作顺序 → 相同合并结果，规则可解释 |
| 冲突可见 | 自动合并无法保留的修改要留痕，用户可查看、可处理 |

### 1.3 非目标（v1 明确不做）

- 跨公网 / 多用户 / 服务器中转，仅局域网 NAS；
- 字段级合并（v1 为记录级合并）；
- NAS 数据端到端加密（清单锁只是应用层鉴权，NAS 上为明文，风险见第七节）；
- 定时 / 自动触发同步（v1 手动触发，自动同步留作后续）；
- 增量二进制协议（v1 全量快照 + 照片按需增量）。

### 1.4 一句话回答「如何保证不存在版本问题」

完全消除版本差异做不到——离线多主场景天然存在并发。但可以做到**「版本无灾难」**：
所有离线修改都不会丢失，合并顺序确定且可解释，输掉的修改留痕可回看。
保证靠五件事：**全局唯一 ID、逻辑时钟版本号、墓碑、记录级 LWW + 冲突副本、WebDAV 互斥锁 + 原子写**。详见第三、四、五节。

## 二、现状盘点（为什么现有数据不能直接同步）

| 现状 | 问题 |
| --- | --- |
| `id` 本地自增（1, 2, 3 …） | 两台设备各自新增物品会撞 id，合并时互相覆盖 |
| `updatedAt` 用墙上时钟 | 设备时钟偏移 → 「后写先到 / 先写后到」判断错误 |
| items 软删、wishes / lists 硬删 | 删除不作为一个「记录」参与同步，同步后会被复活 |
| photos 存绝对路径 | 另一台设备上路径无效，照片无法显示 |
| categories 以名称做主键 | 重命名等于换身份，离线重命名冲突无法合并 |
| 无 INTERNET 权限、无网络库 | 需新增权限与 WebDAV 客户端 |
| 清单锁 / 主题 / 昵称等存 SharedPreferences | 属设备本地设置，不应进入同步 |

## 三、数据模型改造（Room v2 → v3）

### 3.1 全局唯一 ID（解决新建碰撞）

- 每台设备首次启动生成随机 `deviceId`（22 位，写入 SharedPreferences）；
- **新记录 id = (deviceId << 40) | 本地自增 seq**（seq 40 位），主键仍为 `Long`，无需改类型；
- 启用同步时做**一次性迁移**：在单个事务内把所有存量记录重新分配为全局 id，并同步改写引用（`item.listId`、`wish.purchasedItemId`、回收站归属）；
- 迁移后两台设备各自新建的记录 id 永不碰撞。

### 3.2 版本号（逻辑时钟，不依赖墙上时钟）

- `items` / `wishes` / `lists` 增加 `rev: Long` 与 `updatedBy: String(deviceId)`；
- 每次编辑：`rev = max(本地 rev, 同步中看到的远端 rev) + 1`；同 rev 时用 deviceId 字典序做 tiebreak；
- `updatedAt` 保留，仅供界面展示，不参与排序判断。

### 3.3 统一墓碑（解决删除丢失）

- `wishes`、`lists` 增加 `deleted / deletedAt`（items 已有软删字段），**删除一律软删**；
- 墓碑以普通记录的身份参与合并，永远不被「覆盖掉」；
- 墓碑长期保留在快照中（数据量小），v1 不做清理。

### 3.4 分类稳定 id（解决重命名冲突）

- `categories` 增加 `id: String(UUID)` 主键，`name / icon` 变为值；
- items / wishes 仍存分类名用于展示；重命名走「改名事务」；
- 同步合并时以 id 为身份，离线重命名冲突按 rev LWW，输方记录在同步报告中。

### 3.5 照片相对路径

- `photos` 字段改存**文件名**，展示时拼接 `filesDir/photos`；
- 迁移时从绝对路径提取文件名（文件名本身带时间戳 + UUID，天然唯一）。

### 3.6 新增同步元数据表

- `sync_meta`：WebDAV 地址、上次同步时间、上次结果摘要；
- `sync_events`：同步历史（时间、gRev、新增 / 更新 / 删除 / 冲突统计）。

## 四、WebDAV 同步协议

### 4.1 目录布局（用户配置的根路径下）

```
shiwu/
├─ sync.lock        # 互斥锁（If-None-Match: * 原子创建，带租约时间戳）
├─ data.json        # 全量数据快照（gRev + 全部记录含墓碑）
├─ devices.json     # 设备注册表（id / 名称 / 最后同步时间）
└─ photos/…         # 照片文件（按文件名）
```

### 4.2 一次同步的流程（拉取 + 推送合并）

1. 获取锁（重试，超时按租约抢占）；
2. GET `data.json`（远端为空 → 进入首次引导分支）；
3. **合并引擎**：本地 ∪ 远端，按 rev 逐记录 LWW，产出合并结果 + 冲突副本 + 同步报告；
4. 上传照片（本地有、远端无）；
5. 下载照片（远端有、本地无），并把引用写进本地库；
6. PUT `data.json`（新 gRev）+ PUT `devices.json`；
7. 释放锁，本地写 `sync_events`；
8. 展示同步报告：新增 n / 更新 m / 删除 k / 冲突 c。

### 4.3 首次配置的三种引导

| 本地 | 远端 | 处理 |
| --- | --- | --- |
| 有数据 | 为空 | 本地上传为基线 |
| 空（仅自动默认清单） | 有数据 | 整体采纳远端 |
| 有数据 | 有数据 | 直接按 rev 合并，不弹「二选一」 |

### 4.4 并发与原子性

- 「下载 → 合并 → 上传」全程持锁，第二台设备同时触发会等待重试；
- 锁文件用 `PUT … If-None-Match: *` 原子创建，内容含 deviceId + 时间戳；超过租约（如 5 分钟）可强制抢占，防崩溃死锁；
- 上传使用临时文件 + MOVE 覆盖，避免半截文件被读到。

## 五、冲突策略（回答版本问题的核心）

### 5.1 自动合并规则

| 场景 | 处理 |
| --- | --- |
| 两端新增不同记录 / 清单 | 并集，各自保留 |
| 同一记录两端都改 | rev 大者胜（同 rev 比 deviceId），输方存为「冲突副本」 |
| 一端改、一端删 | 按 rev 判：删除胜 → 被覆盖的修改进冲突副本；修改胜 → 删除失效 |
| 两端都删 | 保留一个墓碑 |
| 清单被一端删、另一端往其中加物品 | 物品不丢：若物品本身未删，自动归入「我的物品」并计入同步报告 |
| 分类重命名冲突 | LWW，分类名以胜方为准，输方记录在同步报告 |
| 已购心愿 `purchasedItemId` | 两端都做过全局 id 迁移，引用随 id 映射保持一致 |

### 5.2 冲突副本

- 输方内容存为一条新记录（物品 / 心愿），名称追加「（冲突副本）」，带 `conflictOf` 标记与来源设备 / 时间；
- 不打断自动同步；「同步记录」页可查看，可手动删除或保留；
- 原则：**宁可多一条副本，不可丢任何一条修改**。

### 5.3 一致性保证小结

- 每台设备合并结果一致 → 最终一致；
- 不依赖墙上时钟判断先后；
- 无静默覆盖，所有「输掉」的修改都留痕。

## 六、照片同步

- DB 只存文件名；同步对比本地引用集合与远端 photos 目录，上传缺失 / 下载缺失；
- 同名文件视为同一张（文件名生成时已含 UUID）；
- 删除 GC：合并后确认无任何记录引用，才删除本地与远端文件（保守执行，防止误删他人引用）；
- 同步原图不压缩（NAS 空间换保真；首页展示已有采样解码，不受影响）。

## 七、安全与隐私

- **凭据**：WebDAV 账号密码用 Android Keystore 加密存储，UI 不回显，每台设备独立配置；
- **传输**：局域网 HTTP 明文有被嗅探风险；NAS 支持 HTTPS 时优先 HTTPS；自签证书处理列为待确认决策；
- **NAS 明文**：清单锁只是应用层鉴权（不随数据同步、不包含密码哈希），但同步内容在 NAS 上明文可见；若需保护，后续做「同步载荷加密」（用户口令派生密钥），v1 不做；
- **不随数据同步**：清单锁配置、主题、昵称、first_launch_day、next 计数器。

## 八、界面与交互

- 「我的」页新增「同步」入口（与导入 / 导出并列）：
  - 配置：地址 / 账号 / 密码 / 测试连接；
  - 状态行：上次同步时间、设备列表、本次摘要；
  - 「立即同步」按钮；
- 同步中：进度提示 + 禁止重复触发；失败给出明确错误（连接失败 / 凭据错误 / 锁被占用）；
- 「同步记录」页：每次同步摘要 + 冲突副本列表（可查看 / 删除）。

## 十、待确认决策点

1. **同步模型**：推荐「全量快照 + 互斥锁 + 记录级 LWW」（实现简单、两台设备足够）；备选「操作日志（outbox）」增量更优但复杂度高。需确认。
2. **ID 方案**：推荐保留 `Long`（`deviceId << 40 | seq`），不动主键类型；备选 UUID 字符串主键（改动更大）。
3. **冲突处理**：推荐「自动 LWW + 冲突副本留痕」，不打断同步；若更看重安全可改为「冲突时暂停等人工选择」。
4. **同步范围**：推荐只同步清单 / 物品 / 心愿 / 分类 / 照片；昵称 / 主题 / 锁不同步。
5. **NAS 数据保护**：v1 明文 + 风险提示；是否做载荷加密由你定。
6. **照片**：同步原图（推荐）还是压缩后再同步。
7. **WebDAV 兼容目标**：优先标准实现（群晖 / nginx）；如遇自签证书问题再评估信任方案。

## 十一、风险与边界

- WebDAV 服务差异：`If-None-Match`、`MOVE` 支持不一 → 需对群晖 / nginx 真机验证；不支持时退化为锁内串行写（仍不丢数据）；
- 中途断电 / 崩溃：锁租约 + 临时文件保证可恢复；
- 多设备同时新增同名清单 / 分类：不做去重，名称允许重复（与现状一致），靠 id 区分；
- 照片多时快照体量主要来自照片：清单数据本身很小，照片增量传输缓解；
- 已购转化、回收站等引用关系迁移必须与 id 迁移同事务验证。

## 十二、后续可选项（暂缓）

- 操作日志增量同步 + 多设备规模支持；
